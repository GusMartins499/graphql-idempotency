# graphql-idempotency

English | [Português](README.pt-BR.md)

A study GraphQL API to understand **idempotency keys**: how to make sure that
repeating the same request (double click, retry after a timeout, unstable
network) does not create the same resource twice.

## Stack

- Node.js 24+ (TypeScript runs directly, no build step)
- [GraphQL Yoga](https://the-guild.dev/graphql/yoga-server) with a code-first schema (`graphql-js`)
- [Drizzle ORM](https://orm.drizzle.team/) + SQLite (`node:sqlite`)
- Tests with `node:test`, no external libraries

## Running

```bash
npm install
cp .env.example .env
npm run db:migrate
npm run dev
```

The API starts at `http://localhost:3333/graphql`, with GraphiQL available in the browser.

## How it works here

The `createProduct` mutation requires the `Idempotency-Key` header. Everything
happens inside a single transaction:

| Situation | Result |
|---|---|
| No header | `IDEMPOTENCY_KEY_REQUIRED` error, nothing is created |
| New key | creates the product and stores the key |
| Key already used, same input | returns the product created the first time |
| Key already used, different input | `IDEMPOTENCY_KEY_REUSED` error |

## Trying it in GraphiQL

Open `http://localhost:3333/graphql` and, in the **Headers** tab, enter:

```json
{ "idempotency-key": "my-key-1" }
```

Run it several times:

```graphql
mutation {
  createProduct(input: { name: "Mug", priceCents: 2990 }) {
    id
    name
    priceCents
  }
}
```

- The `id` is always the same.
- Change the key: a new product is created.
- Keep the key and change `priceCents`: `IDEMPOTENCY_KEY_REUSED` error.
- Remove the header: `IDEMPOTENCY_KEY_REQUIRED` error.

## Structure

```
src/
  db/
    schemas/            drizzle tables (products, idempotency_keys)
    migrations/         migrations generated by drizzle-kit
  modules/
    product/
      type.ts           Product GraphQL type
      resolvers/        one GraphQL operation per file
      repositories/     one database access per file
    idempotency/
      repositories/     reading and writing keys
      hash-request.ts   input hash
      errors.ts         IDEMPOTENCY_KEY_* errors
  schema/               Query, Mutation and the final schema
test/                   mirrors src/, with the tests for each module
```

## Known limitations

Simplifications made to keep the focus on the concept, and what would change in
a production system:

- **A single process.** Protection against concurrency relies on SQLite's
  synchronous transaction. With multiple instances and a database like Postgres,
  two requests could both read "key does not exist" at the same time. The
  primary key would prevent the duplicate, but the second request would get a
  unique constraint error instead of the replayed response. The usual fix is to
  store the key first, with an `in_progress` status, and handle the conflict.
- **The replayed response reflects the current state.** The table only stores
  the `id` of the created product, not a copy of the original response.
- **Keys never expire.** In production, they are usually removed after 24 hours
  or a few days.
